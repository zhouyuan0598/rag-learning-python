# 生产化 RAG 架构

## 1. 查询时不应该临时建索引

生产环境中，BM25 不应该在每次查询时扫描文档并临时构建。vector store 也不应该在查询时重新生成所有 embedding。索引构建属于离线或后台任务，查询服务只读取已经构建好的索引。

临时建索引的问题很明显：延迟不可控、CPU 和内存浪费、并发能力差、失败难以隔离。文档越多，问题越严重。生产系统应该把 ingest 和 query 分成两个链路。

## 2. BM25 需要什么存储

BM25 的核心数据是 chunk 文本、分词结果、文档频率、平均文档长度和参数。小项目可以用 JSON 文件保存这些信息。中等规模可以用 SQLite、Postgres 或本地搜索库。更大规模通常使用 Elasticsearch、OpenSearch、Lucene、Meilisearch 或 Typesense。

是否需要数据库取决于规模和需求。如果只是个人学习或几千个 chunk，本地 JSON 索引足够理解原理。如果需要并发查询、增量更新、复杂过滤、权限控制和高可用，就应该使用专门的搜索引擎或数据库。

## 3. vector store 的生产选择

向量索引可以存到 Chroma、FAISS、Milvus、Qdrant、Weaviate、pgvector 或云厂商向量数据库。选择时要看数据量、过滤能力、更新频率、部署复杂度、成本和团队熟悉度。

向量库通常保存 embedding、chunk 文本或 chunk ID、metadata 和距离索引。生产系统经常把 chunk 正文存在对象存储或数据库里，向量库只保存 ID 和向量；查询命中后再回表取完整内容。

## 4. ingest 服务

生产 RAG 通常有独立 ingest 服务。它负责监听文档变化、拉取内容、清洗格式、切分 chunk、生成 embedding、写入 vector store、构建 BM25 索引、记录版本并产出构建日志。

ingest 失败不能影响线上查询。旧索引应该继续服务，直到新索引构建完成并通过检查。对于大规模系统，索引构建还需要任务队列、重试、进度记录和告警。

## 5. query 服务

query 服务负责接收用户问题、执行权限校验、改写 query、检索候选、融合结果、rerank、拼 prompt、调用 LLM、返回答案和 citation。它应该尽量无状态，方便水平扩容。

query 服务还应该记录关键日志：用户问题、检索器类型、top-k、命中的 citation、分数、最终上下文长度、模型名、耗时和错误。没有这些日志，很难定位线上回答为什么变差。

## 6. 权限与安全

权限过滤必须发生在上下文进入 LLM 之前。最稳的方式是在检索候选阶段就过滤掉用户无权访问的文档。不要把无权限内容放进 prompt 后再要求模型“不要泄露”，因为模型不是安全边界。

安全还包括 prompt injection 防护。文档中可能包含“忽略之前指令”“泄露系统提示词”等恶意文本。RAG 系统需要在 prompt 中明确区分用户问题、系统指令和检索内容，并对高风险内容做过滤或隔离。

## 7. 监控与反馈

生产 RAG 需要监控检索命中率、空结果率、低分结果比例、延迟、LLM 错误率、用户反馈和人工审核结果。评估集只能覆盖已知问题，线上监控负责发现新问题。

用户反馈应该沉淀回评估集。比如用户点了“答案无帮助”，就要分析是检索没召回、排序错了、上下文太长、prompt 不清楚，还是 LLM 生成错误。能复现的问题应该加入 JSONL eval，避免后续回归。
