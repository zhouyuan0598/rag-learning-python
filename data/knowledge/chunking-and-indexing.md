# Chunking、Overlap 与索引生命周期

## 1. 为什么要切分 chunk

大多数真实文档都比一次检索结果需要的上下文长。Chunking 是把长文档拆成较小文本块的过程，让检索器可以返回最相关的一小段，而不是整份文档。一个好的 chunk 应该表达一个相对完整的语义单元，例如一个概念定义、一段操作步骤或一个故障原因。

chunk 太大会带来噪音。比如用户只问 “BM25 的 b 参数是什么”，如果返回的是一整篇检索理论文档，LLM 会同时看到 BM25、RRF、reranker、nDCG 等内容，答案更容易跑偏。chunk 太小又会丢上下文，例如问题、原因和解决方法被拆到三个不同 chunk 里。

## 2. chunk size 的取舍

chunk size 是每个文本块的目标长度。较大的 chunk 通常提高 recall，因为答案更可能被同一个块包含；但它会降低 precision，因为返回内容里无关句子更多。较小的 chunk 通常提高 precision，因为文本更聚焦；但它会降低 recall，因为完整答案可能被切碎。

学习阶段可以从 500 到 1000 字符开始试验。文档结构清晰时，可以按标题、段落和列表做结构化切分。代码库可以按函数、类、模块或 Markdown 章节切分。生产系统通常不会只使用固定字符长度，而会结合文档结构和 token 长度。

## 3. overlap 的作用

overlap 是相邻 chunk 之间保留的一小段重复文本。它的主要作用是缓解边界问题。比如 “索引更新策略” 的定义写在前一个 chunk 的末尾，具体步骤写在下一个 chunk 的开头；没有 overlap 时，两边都可能不完整。

overlap 也有成本。重复文本会增加索引体积，可能让多个相邻 chunk 同时被召回，导致 top-k 被相似内容占满。如果 overlap 太大，检索结果看似命中很多，其实信息重复。常见做法是把 overlap 设置成 chunk size 的 10% 到 20%，再用评估集验证。

## 4. 元数据比想象中重要

每个 chunk 不应该只有文本，还应该带上 source、title、section、更新时间、权限标签、文档类型和业务域等元数据。metadata filter 可以在检索前缩小候选范围，例如只查产品手册、只查某个版本、只查用户有权限的空间。

元数据也帮助排查问题。当 eval 发现某个问题没有命中，开发者需要快速知道错误结果来自哪份文档、哪个章节、哪个 chunk。没有 metadata 的 RAG 系统会很难调试，只能看到一段孤立文本。

## 5. ingest 不是查询的一部分

`uv run rag ingest data/knowledge` 的作用是把知识目录里的文档加载、切分并写入索引。它应该在文档准备或文档更新时执行，而不是在每次用户查询时执行。查询服务应该使用已经构建好的索引，这样延迟和稳定性更可控。

本项目现在会同时写 vector store 和 BM25 store。vector store 保存向量相关数据，BM25 store 保存关键词检索需要的倒排统计和 chunk 文本。生产系统里，这两类索引可能存储在不同系统中，但生命周期应该一致：同一批文档、同一套 chunk、同一个版本号。

## 6. 全量索引与增量索引

全量索引是每次从头读取所有文档，重新切分并重建索引。它简单可靠，适合小数据集和学习项目。缺点是数据量大时耗时长，而且重建期间要考虑线上索引切换。

增量索引只处理新增、修改或删除的文档。它需要文档 ID、内容 hash、更新时间和删除标记。实现难度更高，但生产价值更大。一个常见策略是先用全量索引跑通链路，再在文档规模变大后加入增量更新和索引版本切换。

## 7. 索引版本与回滚

索引文件应该带版本信息。版本可以记录 chunk 参数、embedding 模型、BM25 参数、构建时间和文档快照。这样当评估结果突然变差时，可以定位是文档变了、chunk 参数变了，还是 embedding 模型变了。

生产环境最好支持蓝绿切换。新索引构建完成并通过 smoke eval 后，再把查询服务切到新版本。如果新版本出问题，可以快速回滚到旧索引。这个思想和应用部署类似：索引也是线上系统的一部分。
