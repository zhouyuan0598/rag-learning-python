# RAG 常见失败模式与排查

## 1. 知识缺失

第一类失败是知识库根本没有答案。无论 BM25、vector 还是 reranker，都不能从不存在的文档里找到证据。表现通常是检索结果看起来相关但没有直接答案，LLM 可能开始猜测。

排查方法是先人工搜索知识库，确认答案是否存在。如果不存在，就需要补文档、补 FAQ、接入新的数据源，或者让系统明确回答“知识库中没有找到依据”。不要用 prompt 强迫模型回答没有资料的问题。

## 2. chunk 切分错误

第二类失败是切分问题。chunk 太大导致上下文噪音多，chunk 太小导致答案依据被拆散。标题和正文分离、表格被截断、步骤列表被切开，都会影响检索和生成。

排查时要看命中的 citation 和 chunk 原文。如果正确文档被命中但答案仍然不完整，可能是 chunk 边界不合理。可以调整 chunk size、overlap，或者改成按标题和段落的结构化切分。

## 3. 召回失败

召回失败是正确 chunk 没有进入 top-k。BM25 召回失败通常是因为 query 和文档词不一致、分词不合适或关键词太少。向量召回失败可能是 embedding 模型不适合领域、文本太短或语义过于细。

缓解方法包括 query rewrite、同义词扩展、metadata filter、hybrid search、增加候选池和改进 embedding 模型。召回失败优先看 recall@k，因为正确资料没被找回来时，后续 rerank 和 prompt 都救不了。

## 4. 排序失败

排序失败是正确 chunk 进入候选集但排得太靠后。表现是 recall@k 还可以，但 MRR 或 precision 较低。LLM 看到的前几个 chunk 可能是相似但不直接回答问题的内容。

缓解方法包括 reranker、RRF 参数调整、按问题类型路由和减少无关候选。排序问题不要只看 retrieval_hit_rate，因为 hit 只说明“至少找到了一个”，并不说明它排得好。

## 5. 查询表达问题

用户问题可能太短、上下文缺失、术语不一致或包含多重意图。比如“这个怎么配置”没有说明“这个”指什么；“报错了怎么办”没有错误码；“权限问题”可能指登录权限、文档权限或接口权限。

缓解方法包括澄清问题、query rewrite、对话历史补全、业务域过滤和结构化入口。对于企业知识库，很多检索失败不是算法问题，而是 query 缺少必要上下文。

## 6. 上下文组装问题

即使检索结果正确，prompt 组装也可能出错。上下文顺序混乱、citation 丢失、重复 chunk 太多、超过模型上下文窗口、系统指令不清楚，都会影响最终答案。

排查时要保存最终 prompt 或至少保存上下文列表。只看检索结果不够，因为 LLM 实际看到的是组装后的 prompt。生产系统应该记录上下文长度、chunk 数量、citation 和截断策略。

## 7. 生成阶段问题

LLM 可能没有严格根据上下文回答，或者把多个 chunk 的信息错误合并。它也可能在证据不足时编造答案。这个阶段的问题需要引用约束、拒答策略、答案格式约束和事实一致性检查。

如果检索指标很好但用户仍然认为答案差，就要进入生成质量评估。可以用人工审核、LLM-as-judge、引用一致性检查和 golden answer 对比。不要把所有问题都归咎于检索器。

## 8. 一套排查顺序

实用排查顺序是：先确认知识是否存在，再看 chunk 是否合理，再看 recall@k，再看 MRR 和 precision@k，再看 prompt 组装，最后看 LLM 生成。这个顺序能避免盲目调参。

每次发现失败案例，都应该把它变成 eval case。评估集不是一次性文件，而是系统学习经验的沉淀。只要线上或手工测试发现一个有代表性的问题，就应该补充 question、expected_answer 和 expected_citations。
