# Query Rewrite 与检索路由

## 1. 为什么要 query rewrite

用户的问题经常不适合直接拿去检索。问题可能太短、缺少上下文、口语化、包含代词，或者同时问了多个意图。Query rewrite 的作用是把用户原始问题改写成更适合检索的查询表达。

例如用户问“这个怎么开”，对话历史里刚提到“增量索引”，系统可以把查询改写成“增量索引如何开启和配置”。再比如用户问“precision 低怎么办”，可以扩展成“precision@k 低说明上下文噪音多，如何通过 top-k、threshold、reranker 缓解”。

## 2. rewrite 的风险

query rewrite 不能随意发散。改写后的查询如果加入了用户没有表达的假设，可能把检索带偏。一个好的 rewrite 应该补全上下文、规范术语、拆分意图，但不能改变问题本身。

生产系统通常会保存 original query 和 rewritten query，方便排查。如果评估发现改写后效果更差，可以回看改写文本，判断是模型理解错了，还是检索器本身不适合这个问题。

## 3. 检索路由

检索路由是根据问题类型选择检索策略。包含错误码、函数名、配置项和精确字段的问题，可以优先走 BM25 或提高 BM25 权重。自然语言解释、同义改写和概念类问题，可以优先走向量检索。

路由不一定是二选一。很多系统会默认 hybrid，但对不同问题调整候选数量和权重。例如代码问题增加 BM25 候选，政策解释问题增加向量候选，时间敏感问题先按 metadata 过滤最新版本。

## 4. 多意图问题

用户可能一次问多个问题，例如“BM25 是什么，和向量检索有什么区别，生产环境怎么存”。如果直接用整句检索，结果可能混杂。更稳的做法是把问题拆成多个子查询，分别检索，再合并上下文。

多意图拆解会增加复杂度。系统需要决定子问题数量、每个子问题的 top-k、合并去重策略和最终回答结构。学习项目可以先通过手写评估问题观察这类失败，再考虑自动拆解。

## 5. rewrite 与评估

query rewrite 必须进入评估闭环。只看最终答案无法判断 rewrite 是否有帮助。评估日志应该记录原始问题、改写问题、检索结果和最终答案。这样才能知道提升来自改写、检索器、reranker 还是 prompt。

常见实验方法是 A/B 对比：同一批 eval cases，一次直接检索，一次启用 rewrite，对比 recall@k、precision@k、MRR 和延迟。如果 rewrite 提升很小但延迟增加很多，就不一定值得上线。
