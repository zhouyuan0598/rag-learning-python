# RAG 基础与端到端流程

## 1. RAG 的定义

RAG 是 Retrieval-Augmented Generation 的缩写，中文通常叫检索增强生成。它的核心思想是：模型回答问题前，先从外部知识库检索相关资料，再把这些资料作为上下文交给大语言模型生成答案。这样做可以把模型的语言能力和企业、团队、项目里的实时知识结合起来。

一个简单的判断标准是：如果问题依赖一批可以更新的文档、手册、代码、政策或记录，就优先考虑 RAG。如果问题主要是固定格式转换、语气风格、分类标签或结构化抽取，微调或普通提示词可能更直接。RAG 不是让模型记住更多事实，而是让模型在回答时看见证据。

## 2. 最小 RAG 流程

一个最小 RAG 系统通常包含七步：加载文档、切分 chunk、生成 embedding、写入检索索引、根据用户问题检索相关 chunk、构造 prompt、让 LLM 基于上下文生成答案。这个项目里的 `rag ingest` 对应前四步，`rag ask` 对应后面三步。

加载文档负责把 Markdown、文本、PDF 或网页内容变成统一的 Document。切分 chunk 负责把长文档拆成适合检索的文本块。embedding 模型把文本变成向量。vector store 负责保存向量并返回相似结果。LLM 最后只应该根据检索上下文回答，并尽量附带 citation。

## 3. RAG 适合解决的问题

RAG 适合知识经常变化、需要引用来源、需要接入私有文档、需要快速上线的场景。比如企业知识库问答、产品手册助手、客服知识库、合规政策查询、代码库问答、运维故障助手和学习笔记问答。

这些场景的共同点是事实来源很重要。用户不仅想要答案，还想知道答案来自哪份资料。如果文档明天更新了，系统应该通过重新索引或增量索引看到新内容，而不是重新训练模型。

## 4. RAG 的边界

RAG 不能自动保证答案正确。检索错了，LLM 就会拿错上下文回答；检索太宽，LLM 会被无关内容干扰；检索太窄，关键证据可能缺失。RAG 的质量首先取决于知识库质量、chunk 策略、检索召回、排序和 prompt 约束。

RAG 也不能替代权限控制。生产系统必须在检索前或检索时执行权限过滤，避免用户看到不该看到的 chunk。一个常见原则是：用户没有权限访问的文档，不应该进入候选集，更不应该被塞进 prompt。

## 5. 学习项目里的关键对象

这个项目把 RAG 拆成几个容易观察的对象：Document 是原始文档，Chunk 是切分后的文本块，RetrievedChunk 是带分数的检索结果，Retriever 是统一检索接口，LLMClient 是回答生成接口。这样可以单独替换检索器，而不必重写评估逻辑。

`vector` 检索使用 embedding 和向量相似度。`bm25` 检索使用关键词匹配和词频统计。`hybrid` 检索把多个检索器的结果融合。评估命令会记录命中的 citation、recall、precision、MRR、分数和耗时。

## 6. 一次查询的数据流

用户提出问题后，系统先把问题交给 retriever。retriever 返回 top-k 个 chunk。随后 prompt builder 把问题、上下文和回答要求组织成提示词。LLM 根据提示词生成答案。最后系统把答案、引用和调试信息返回给用户。

在离线学习模式下，项目使用 OfflineContextLLM，它不会调用真实大模型，而是把检索到的上下文拼出来。这让你可以把注意力放在检索质量上。只要 expected_answer 出现在检索上下文里，answer_contains_expected_rate 就可能变高；这不是完整的生成质量评估。

## 7. 生产 RAG 的基本要求

生产 RAG 需要稳定的索引文件或数据库、可重复的 ingest 流程、清晰的版本记录、权限过滤、失败告警、评估集和人工反馈闭环。只有 demo 阶段才适合每次查询临时扫描全部文档。

一个更稳的生产路径是：文档变更触发索引任务，索引任务生成 vector index 和 BM25 index，服务查询时只读取已构建好的索引。查询服务不负责重建全量索引，只负责加载索引、执行检索、重排、拼 prompt 和生成答案。
