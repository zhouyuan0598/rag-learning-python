# RAG 检索实验知识库

## 1. RAG 基础定义

RAG 是 Retrieval-Augmented Generation 的缩写，中文通常叫检索增强生成。它的核心思想是：不要只依赖大语言模型参数里记住的知识，而是在回答前先从外部知识库检索相关内容，再把检索结果作为上下文交给模型生成答案。

一个最小 RAG 流程通常包括：加载文档、切分 chunk、生成 embedding、写入检索存储、根据问题 retrieve 相关 chunk、构造 prompt、生成答案并引用来源。这个项目刻意把这些步骤拆开，方便观察每一步如何影响最终回答。

## 2. Chunking 与 overlap

Chunking 是把长文档切成较小文本块的过程。chunk 太大时，检索结果可能包含很多无关内容，影响 precision；chunk 太小时，相关上下文可能被切碎，影响 recall。合适的 chunk size 取决于文档结构、问题类型和模型上下文窗口。

Overlap 是相邻 chunk 之间保留一小段重复内容。它可以减少边界信息丢失，例如一个定义跨越两个 chunk 时，overlap 能让检索结果仍然包含完整语义。代价是索引里会有重复文本，存储和检索噪音都会增加。

## 3. BM25 关键词检索

BM25 是经典关键词检索算法，可以理解为更实用的 TF-IDF 排序方法。它根据 query 词是否出现在 chunk 中、出现次数、词的稀有程度以及文档长度归一化来计算相关性。BM25 不理解深层语义，但对精确术语、产品名、错误码、函数名、配置项和编号很稳。

BM25 的优势是可解释、无需训练、对专有词敏感。如果用户问 BM25、RRF、Chroma、API key、HTTP 500 这类精确词，关键词检索经常比向量检索更可靠。它的弱点是同义改写能力差，如果问题和文档使用不同说法，BM25 可能找不到。

## 4. 向量检索与 embedding

向量检索会把文本编码成 embedding，也就是一组数字向量。语义相近的文本，向量距离通常更近。比如用户问“RAG 适合什么业务”，文档写“企业知识库问答、文档助手、客服助手”，即使字面词不完全一致，向量检索也可能找到相关 chunk。

向量检索擅长自然语言改写、概念解释和语义相似问题。它的风险是精确词可能被稀释，尤其是代码符号、版本号、人名、短缩写和冷门领域词。embedding 模型的训练语料和语言覆盖也会影响检索质量。

## 5. Hybrid Search 与 RRF

Hybrid Search 是混合检索，目标是同时利用 BM25 的关键词稳定性和向量检索的语义泛化能力。常见做法是先分别运行 BM25 和 vector search，得到两批候选 chunk，然后合并去重并重新排序。

RRF 是 Reciprocal Rank Fusion。它不直接相加 BM25 分数和向量相似度，而是根据排名融合：排第 1 的结果加分最多，排第 10 的结果加分较少。如果一个 chunk 在多个检索器里都排得靠前，RRF 会把它推到更前面。RRF 适合学习阶段，因为不同检索器的原始分数不在同一量纲。

## 6. Reranker 与两阶段检索

Reranker 是第二阶段排序器。第一阶段先用 BM25、vector 或 hybrid 粗召回 top-20，第二阶段把 query 和每个候选 chunk 放在一起判断相关性，再重排出 top-5 交给 LLM。这样做通常比只靠单次向量检索更准。

Reranker 的代价是速度更慢，因为它要逐个比较 query 和候选 chunk。因此生产系统通常不会对全库所有 chunk 做 rerank，而是先召回一小批候选。典型流程是：粗召回 top-20，rerank top-5，构造 prompt，生成答案。

## 7. 检索评估指标

recall@k 衡量正确 chunk 有没有被前 k 个结果找回来。它的计算方式是：前 k 个结果命中的正确 citation 数除以全部正确 citation 数。RAG 里 recall 很关键，因为正确资料找不回来，LLM 后面无法可靠回答。

precision@k 衡量前 k 个结果里有多少是真的相关。它的计算方式是：前 k 个结果中正确 citation 数除以前 k 个结果数。precision 低说明塞给 LLM 的上下文噪音多，模型更容易被无关内容干扰。

MRR 是 Mean Reciprocal Rank，关注第一个正确结果排第几。第一个正确结果排第 1，得分是 1；排第 2，得分是 0.5；没找到，得分是 0。MRR 能反映正确答案是不是排得足够靠前。nDCG 适合有相关性等级的评测集，越相关的结果越应该排在越前面。

## 8. RAG 与微调

RAG 和微调解决的问题不同。RAG 更适合知识经常变化、需要引用来源、需要接入私有文档、需要快速更新知识库的场景。只要更新外部文档并重新索引，就能让系统利用新知识。

微调更适合改变模型行为、输出风格、领域表达习惯或固定任务格式。微调不适合频繁注入事实知识，因为每次知识变化都重新训练成本很高，也难以保证引用来源。很多真实系统会同时使用 RAG 和微调：RAG 提供事实依据，微调改善表达和任务遵循。

## 9. 常见应用场景

RAG 常用于企业知识库问答、文档助手、客服助手、代码知识库问答、合规政策查询、产品手册问答和内部运维助手。这些场景通常要求答案基于最新资料，并且能说明来源。

在代码知识库中，BM25 对函数名、类名、错误码和配置项很有用；向量检索对“这段逻辑在哪里处理权限校验”这类自然语言问题更有用；Hybrid Search 可以同时覆盖精确符号和语义描述。

## 10. 常见检索失败模式

第一类失败是切分问题：chunk 太大导致上下文噪音多，chunk 太小导致答案依据被拆散。第二类失败是召回问题：正确 chunk 没有进入 top-k，后续生成必然缺少依据。第三类失败是排序问题：正确 chunk 被排在很后面，LLM 可能先看到无关内容。

第四类失败是查询表达问题：用户问题太短、术语不一致或缺少上下文，检索器难以匹配。可以用 query rewrite、metadata filter、Hybrid Search 或 reranker 缓解。评估集的作用就是把这些失败模式量化，让每次优化都有证据。
